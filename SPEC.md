# ТЗ: нарезка немецкого текста на блоки

## 0. Коротко (ответы заказчика, итерация 1)

| Вопрос | Ответ |
|---|---|
| Что получить в руки? | правило-инструкцию + работающую программу + валидатор |
| Зачем блоки? | заучивание немецкого: блок — смысловая фраза для произнесения и повтора |
| Объём за один раз | до страницы; текст копируется из документов |
| Язык | только немецкий (алгоритм — язык-агностик) |
| Что важнее | резать там, где нужна пауза: **лишний рез лучше пропущенной паузы** |
| Интернет | не нужен, всё офлайн |
| Для кого | личное использование |

## 1. Принципы правильной нарезки

1. Блок — смысловая фраза на одном дыхании: **2–6 слов** (7 — предупреждение, 8+ — ошибка).
2. Рез там, где человек делает паузу для вдоха или смыслового ударения.
3. Блок не заканчивается служебным словом; рез сразу после предлога не делается.
4. Рез между существительным и его предложным определением **разрешён**.
5. Слово не разрывается, блок не начинается со знака, кавычка не открывается без пары.

Точные числа, коды нарушений и исключения — `RULE.md` §§1–3.

## 2. Рамки: чего сознательно не делаем

| Не делаем | Почему |
|---|---|
| озвучка (TTS) | не требуется |
| сеть, онлайн-сервисы | офлайн |
| передача другим | личное использование; GPL-зависимости (SoMaJo) не подключаем |
| правка текста | разбивка не меняет слова, кавычки и опечатки |
| обучение своей модели до 150 размеченных | мало данных; вернёмся после полной разметки |

Битые предложения (сломанные кавычки, дефисы, неразрывные пробелы) чинятся автоматически
и размечаются, а не отбрасываются (`rule/normalize.py`, `RULE.md` §6).

## 3. Как работаем

1. Заказчик размечает предложения в `data/*.md`: пауза = ` / `, сомнительное место = ` /? `.
2. Собирается машинный набор, прогоняются аудит и валидатор; показываются расхождения.
3. Правило правится **данными** (`rule/config.json`), не кодом.
4. Нарезчик режет новые тексты, валидатор проверяет любую разбивку.

## 4. Состав решения

| Что | Где |
|---|---|
| правило | `RULE.md` |
| нарезчик / валидатор | `rule/segment.py` / `rule/validator.py` |
| числа правила | `rule/config.json` |
| разметка и машинные наборы | `data/*.md`, `bench/sets/*.jsonl` |
| MCP-сервер | `MCP-stanza-german/server.py` |

Все отслеживаемые пути — ASCII: кириллические имена искажались при распаковке архивов
и мешали установщику найти `config.json`; контракт проверяет `scripts/check_ascii_tree.py`.

## 5. Как устроено

- **Оценка границы**: расстояние между соседними словами по дереву зависимостей Stanza (S1).
- **Выбор нарезки**: динамическое программирование с учётом длины блока (цель — 3 слова).
- **Запреты жёсткие** (`RULE.md` §2), **штрафы мягкие** (`RULE.md` §3).
- Валидатор различает ошибку, предупреждение и штраф; нарезчик и валидатор читают одни числа
  из `rule/config.json`.
- MCP отдаёт те же возможности: `segment_german`, `check_segmentation`, `parse_german`,
  `rule_info`, `rule_self_test`, `pipeline_info`.

## 6. Как проверяем качество

Главная мера — доля блоков, которые заказчик не взял бы (цель < 5%); техническая F1 печатается
рядом для сравнения алгоритмов. Текущие числа, их источник и объяснение — `RULE.md` §4
и `rule/config.json`; эталон приёмки зашит в `installer/lib/checks/acceptance.py`.

Дополнительно: разметка 52 проходит валидатор целиком, 102 из 103 предложений собираются
обратно в исходный текст символ в символ.
