# План работ: от правил к готовому алгоритму

**Принцип:** сначала быстрый черновик, потом улучшение (ваше Q15). Каждый этап заканчивается
измеримым результатом, а не «стало красивее».

---

## Что делаем и в каком порядке

| Этап | Что | От кого зависит | Время | Результат |
|---|---|---|---|---|
| **0** | Зафиксировать решения (Q1–Q5, Q16–Q20) | **вы** (10 мин) | — | `РЕШЕНИЯ_ЗАКАЗЧИКА_v2.md` заполнен |
| **1** | `segment.py`: дерево составляющих + DP (метод A2) | — | 1 день | рабочий генератор + замер на 52 |
| **2** | Делитель предложений: SoMaJo перед Stanza | — | 0.5 дня | «страница целиком» работает без ошибок на «:», «;», датах |
| **3** | Переразбивка 52 вами | **вы** (40–60 мин) | — | 52 «учебных» предложения в новом формате |
| **4** | Настройка весов на вашей новой разметке | этап 3 | 0.5 дня | F1 + доля плохих блоков до/после |
| **5** | Оценка A1 (MLM: «где была бы запятая») + сравнение с A2 | 1 скачивание модели | 1–2 дня | таблица «метод → F1 / плохие блоки» |
| **6** | Валидатор: новые ограничения (min 2, cap 7, после служебного слова, внутри PP) | этап 0 | 0.5 дня | `check` проверяет ваши новые правила |
| **7** | 150 предложений (heldout) — финальная оценка | **вы** (2–3 часа, позже) | — | цифры «на незнакомом материале» |

и 2–3 часа позже (150).

## Этап 1 подробно: что именно будет написано

Один модуль `reference/segment.py`, ~200 строк, без новых зависимостей:

```python
def segment(sentence, parse, params) -> list[str]:
    """
    1. parse — разбор Stanza (constituency + depparse + upos), уже есть в MCP
    2. score[i] для каждой границы между словами i-1 и i:
         - расстояние между листьями в дереве составляющих, нормированное в 0..1
         - + бонус, если слева запятая/двоеточие/тире
         - + бонус, если это конец придаточного (по дереву зависимостей)
    3. запрещённые позиции (hard constraints):
         - нельзя резать после артикля/предлога/союза/частицы (Q4)
         - нельзя резать внутри предложной группы (Q3)
         - нельзя резать внутри MWT, между «zu» и инфинитивом
    4. DP: максимизируем  Σ score(резы) − w_len·Σ|ideal − len(блок)|
         при  min_words=2, max_words=7
    5. возвращаем блоки
    """
```

Параметры (все — числа в `config.json`, не код):

| Параметр | Смысл | Стартовое значение |
|---|---|---|
| `min_words` | минимум слов в блоке | 2 |
| `ideal_len` | «идеальная» длина | 4 |
| `max_words` | максимум слов | 7 |
| `w_len` | насколько сильно держаться идеала (меньше → больше резов, Q5) | 1.0 |
| `comma_bonus` | бонус за рез после запятой | 0.3 |
| `clause_bonus` | бонус за границу клаузы | 0.5 |
| `forbid_after_upos` | после каких слов резать нельзя (Q4) | `[ADP, DET, CCONJ, SCONJ, PART]` |

**Почему это «готовое решение», а не самоделка:** схема (оценка границ + beam search/DP +
штраф за длину) — это опубликованный и работающий подход: subtitle2go (Apache-2.0, в
production у лекционного портала Гамбургского университета) и метод из EMNLP-2024
(лучший по F1 среди всех методов в статье). Мы берём схему и подставляем ваш парсер.

## Этап 6 подробно: что станет с `rule.py`

`rule.py` остаётся **судьёй** (это его роль по ТЗ §0.1), но набор проверок сокращается:

| Проверка | Сейчас | Станет |
|---|---|---|
| покрытие предложения блоками | да | да |
| `min` = 2 слова | да | да |
| `cap` = 7 слов | да | да |
| пунктуация (P1/P2) | да | да |
| 14 классов швов (C1–C14) | да, как «можно/нельзя» | **нет**: заменяются оценкой алгоритма |
| 6 запретов (NO-CUT) | да | 3: MWT, `zu`-инфинитив, «не после служебного слова» |
| ранг вариантов | да (перебор) | не нужен: DP даёт один вариант |

Из 20 правил остаётся ~6. GAP-реестр (G6–G15) закрывается: «дыр» больше нет — есть веса.
Прежние классы сохраняются в документации как **объяснения** («этот рез — граница PP»),
но перестают управлять генерацией.

Побочный эффект: **снимается открытое решение №49** (в коде `rule.py` пороги C3/C5 были 3/3,
а в `config.json` 2/2). Если классы перестают управлять генерацией, расхождение исчезает само;
до этого решения по нему не требуется.

## Что НЕ делаем (и почему)

| Не делаем | Почему |
|---|---|
| Дальше писать классы правил C15, C16… | замер: 20 правил дают F1 0.20, ноль правил — 0.27–0.38 |
| Жёсткое правило по слогам | ваша формулировка ломает 12% ваших же блоков (замер §3.3 в `02_ЗАМЕРЫ.md`) |
| Переписывать Festival / Maguer | это 1996–2014, правила под другой язык/задачу; берём только идеи |
| Озвучка | ваше решение Д-01 |
| Облачные LLM | ваше решение Q9 (только офлайн) |
| Обучение своей модели прямо сейчас | нет разметки; вернёмся после 150 (Путь 2) |

## Гейты (когда этап считается сданным)

1. **Этап 1:** `segment.py` даёт на 52 предложениях F1 ≥ 0.35 и **не падает** ни на одном
   предложении из 150 (проверка на устойчивость).
2. **Этап 2:** на 19 «трудных» кейсах 19/19 правильных границ предложений; на 30 «страницах» 30/30.
3. **Этап 4:** F1 на новой разметке **выше**, чем на старой (иначе веса не те).
4. **Этап 5:** таблица «A2 vs A1 vs A2+A1» с цифрами; выбираем по доле плохих блоков.
5. **Этап 6:** `rule.py check` на новом корпусе = 100% compliant (гейт регресса).
6. **Этап 8:** MCP-инструмент отвечает на «страницу» за < 5 с и возвращает блоки + объяснение.

## Риски и как их снимаю

| Риск | Вероятность | Что делаю |
|---|---|---|
| Constituency-парсер Stanza ошибается на длинных юридических предложениях (6/52 не совпало по числу слов) | средняя | fallback на дерево зависимостей (A3) для таких предложений; логируем |
| F1 ~0.35 вас не устроит | средняя | этап 5 (MLM) обычно даёт +0.05…+0.08; этап 7 (обучение на вашей разметке) — ещё больше |
| Ваша разметка сильно отличается от «средней» (вы режете семантически, а не синтаксически) | высокая | именно поэтому этап 3 и 4: веса настраиваются на вас, а не на «среднего немца» |
| SoMaJo GPL-3.0 | низкая | для личного использования ограничений нет; если когда-то будете распространять — заменим на своё правило (Stanza + 4 регулярки) |
