**Решение заказчика (базовое):** «ищем и опробуем алгоритмы, не зацикливаемся на немецком».

иначе алгоритм перерезает длинные предложения.

---

## 1. Правило отбора

Берём **только то, что можно реализовать за 1–2 дня и измерить на ваших 52 примерах**.
Каждый алгоритм должен:

1. работать **офлайн** (ваше Q9);
2. не требовать обучения на разметке (её пока нет — Q7), либо требовать только настройки
   3–5 числовых параметров;
3. быть **язык-агностиком** (или явно помечен как «немецкий»);
4. давать **одну** нарезку (а не 5 «допустимых», как сейчас);
5. укладываться в 2–3 секунды на страницу.

Что **не** берём: перевод/перефразирование, озвучку (Д-01), облачные сервисы (Q9),
модели, требующие GPU.

---

## 2. Общая схема (одна для всех)

У всех алгоритмов **одинаковый каркас**, отличается только «оценка границы»:

```
предложение
   │  Stanza: tokenize + pos + depparse + constituency  (уже есть в MCP)
   ▼
оценка каждой границы  score[1..n-1]  ← ЭТО и есть отличие алгоритмов
   │  + жёсткие запреты (min 2, cap 7, после служебного слова, внутри PP)
   ▼
DP: выбираем набор границ, максимизирующий  Σ score − w·Σ|ideal − длина|
   ▼
блоки
```

Поэтому алгоритмы сравниваются **честно**: каркас и ограничения одинаковые, разница только
в том, «кто» оценивает границу.

## 3. Список алгоритмов

### 3.1. Базовая линия («а нужен ли вообще синтаксис?»)

| ID | Название | Как работает | Зачем нужен |
|---|---|---|---|
| **B0** | Нарезка без резов | всё предложение = 1 блок | нижняя граница; если алгоритм её не бьёт — он бесполезен |
| **B1** | Только пунктуация | рез после каждой `,` `;` `:` `–` | проверка гипотезы «запятая = пауза» (дёшево, без NLP) |
| **B2** | Только длина | жадно: ровно по 4 слова, синтаксис игнорируется | проверка «может, синтаксис и не нужен?» |

### 3.2. Синтаксические оценки (обучения не требуют)

| ID | Название | Источник | Как считаем score |
|---|---|---|---|
| **S1** | LCA по дереву зависимостей | `subtitle2go`, Apache-2.0 | длина пути между соседними словами в дереве зависимостей (нормированная) |
| **S2** | Расстояние по дереву составляющих | Calleja et al., EMNLP-2024, метод №2 | расстояние между листьями в constituency-дереве Stanza |
| **S3** | Тип составляющей на границе | та же идея, но по типам | бонус, если на границе начинается/заканчивается S, SBAR, VP, PP; штраф внутри NP |
| **S4** | Гибрид S1 + S2 | — | среднее двух нормированных оценок (проверка: складываются ли сигналы) |
| **S5** | Наши 14 классов правил | `rule.py` rank1 | текущий подход (для сравнения, не для победы) |

### 3.3. Семантические / статистические оценки (офлайн, без обучения)

| ID | Название | Источник | Как считаем score |
|---|---|---|---|
| **S6** | Семантический «провал» (TextTiling) | Hearst 1997, классика | косинус между векторами левого и правого окна (sentence-transformers, уже стоит локально); чем ниже похожесть — тем вероятнее пауза |
| **S7** | MLM-пунктуация | Ponce et al., ACL 2023 + EMNLP-2024, метод №1 | «поставила бы модель здесь запятую?»: маскируем позицию и суммируем вероятность знаков препинания (нужна gbert-base, ~440 МБ, офлайн после скачивания) |

### 3.4. Обучаемые (позже, когда будет ваша разметка)

| ID | Название | Когда | Что нужно |
|---|---|---|---|
| **L1** | Token classification (B/I/O) на вашей разметке | после 150–300 размеченных предложений | 10–20 мин обучения на CPU, многоязычный BERT |
| **L2** | Fine-tune LLM (LoRA) | если L1 мало | 3–8 ГБ модель, GPU желателен |

Сейчас L1/L2 **не испытываем** — нет данных. Но каркас (DP + ограничения) останется тем же:
модель будет давать score вместо S1–S7.

## 4. Как будем сравнивать

### 4.1. Данные

| Набор | Роль | Когда |
|---|---|---|
| **Корпус 52** (93 реза) | настройка и первичное сравнение алгоритмов | сейчас |
| **150 heldout** | финальный экзамен на незнакомом материале | после вашей разметки (Q7) |

### 4.2. Метрики

| Метрика | Что показывает |
|---|---|
| **exact** | вся нарезка совпала с вашей |
| **P / R / F1 по границам** | насколько точно попадаем в ваши резы |
| **% блоков вне 2–7 слов** | грубые нарушения (должно быть 0 — каркас не даёт) |
| **% блоков, кончающихся служебным словом** | ваше Q4, проверяем фактически |
| **% резов внутри PP** | ваше Q3 |
| **средняя длина блока / разброс** | комфорт для заучивания |
| **время на предложение** | пригодность для «страницы целиком» |

### 4.3. Два режима цифр (чтобы не обмануть себя)

- **«по умолчанию»** — параметры заданы заранее (ideal 4, cap 7, w 1.0). Честный результат «из коробки».
- **«лучшая точка»** — сетка параметров на 52. Верхняя граница.
  Если алгоритм выигрывает только в «лучшей точке», а в «по умолчанию» проигрывает — это
  важный сигнал: он капризный.

### 4.4. Режим для 150 (когда разметки ещё нет)

**Слепой прогон:** алгоритм выдаёт нарезку, вы смотрите глазами и отмечаете плохие блоки
(метрика «доля плохих блоков», см. `03_ОТВЕТ_НА_Q6.md`). Так можно сравнивать алгоритмы
**до** того, как вы разметите все 150.

После разметки тот же прогон даёт exact/P/R/F1.

## 7. Технические детали (для программиста)

- **Каркас:** `bench/segment_core.py` — DP + ограничения (min 2, cap 7, запреты Q3/Q4,
  min-merge), не зависит от языка.
- **Оценки:** `bench/scorers.py` — по одной функции на алгоритм, каждая возвращает
  массив `score[1..n-1]` в диапазоне 0..1.
- **Запуск:** `bench/run_bench.py --set corpus52 [--algo S2] [--grid]`.
- **Зависимости:** Stanza (есть), sentence-transformers + all-MiniLM-L6-v2 (есть локально),
  transformers + gbert-base (S7, скачивается один раз).
- **Лицензии:** Stanza Apache-2.0; sentence-transformers Apache-2.0; all-MiniLM-L6-v2 Apache-2.0;
  gbert-base MIT; код `subtitle2go` Apache-2.0 (используется как референс алгоритма, не копируется).
- **Воспроизводимость:** фиксированные seed, кэш разборов в `bench/cache/`, все цифры
  пересчитываются одной командой.
