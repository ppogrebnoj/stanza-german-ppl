# SPEC: rule.py — детерминированный референс-интерпретатор RULE.md (v3)

## 0. Назначение / контекст / главный риск

**Назначение.** `rule.py` — статичный детерминированный референс-интерпретатор правила `RULE.md` (v3) + его машинальной версии `reference/config.json`. Вход: текст одного предложения + config (пакет: `rule.py` вызывается на каждое отдельно — правило локально; LLM собирает единый ответ по PROMPT). Выход: разбиение `recommended` / `admissible` / `rejected` по данным Stanza (JSON, §8).

**Цель.** Объективная, воспроизводимая и 100%-детерминированная проверка правила по `CORPUS/verified.jsonl` и верификация нового ground-truth-кейса.

**Ключевой принцип.** *Параметры правила = данные (config), алгоритмическая семантика = код интерпретатора.* При v{n+1} патчится только config, если изменение выражается уже поддерживаемой схемой; новая операция/условие требует изменения `rule.py` и тестов.

**Главный риск.** Правило уже в **v3**, есть 3 verified-кейса в `CORPUS/verified.jsonl`, но реального исполнителя нет. Сейчас каждый новый verified-кейс «проверяется» LLM (см. PROMPT шаг D). Если LLM ошибётся в переборе вариантов — ошибка закрепится в ground truth → в v8+ сложно отделить «баг» от «дельты». Без `rule.py` нельзя гарантировать 100% детерминизм и 100% регресс.

**Актуальные данные (после упрощения/реноумерации).** Правило = единый `RULE.md` (v3), конфиг = единый `reference/config.json` (без номера, `"version":"v3"`). Устаревшие ссылки «v7 / config/v7.json» игнорируются.

## 2. Принципы и границы (два слоя)

### 2.1 Слой 1 — статичный интерпретатор (`rule.py`)

Стабилен между версиями, пока версия правила использует поддерживаемые алгоритмические операции. Реализует пайплайн; значения параметров и условия, поддерживаемые схемой, берёт из config.

- `parse` — Stanza depparse (German, v1.15.0). Для дерева зависимостей использовать `Sentence.words`; `Sentence.tokens` — для восстановления исходного текста и отображения MWT. Условия C/NO-CUT/P используют только поля Stanza и дерево зависимостей; constituency-дерево не требуется.
- `build_units` — построение unit по §3.1; MWT неделим на границах реза.
- `seams` — множество позиций реза; C1–C5 реализованы как отдельные чистые функции. Параметры правил — из config, алгоритмическая семантика функций — из `rule.py`.
- `nocut` — запретные позиции реза из `config.json` (§3.3).
- `punct_glue` — обработка P1/P2 из `config.json` (§3.4).
- `min_merge` — детерминированное слияние по `min_merge` (§3.6).
- `cap_check` — проверка лимитов и допустимости границ (§3.7).
- `rank` — ранжирование по §3.8.
- `render` — формирование текста блоков и JSON по §8.

**Граница конфигурируемости.** Изменение значений и условий, уже поддерживаемых интерпретатором, — через `config.json`. Новая операция/тип условия, для которого в `rule.py` нет обработчика, требует изменения кода; **config completeness обязан выявлять такие неподдерживаемые условия, а не считать конфиг полным автоматически**.

### 2.2 Слой 2 — конфиг правила (`reference/config.json`)

Содержит параметры и условия актуальной версии: `version`, `min`, `pref`, `cap`, правила NO-CUT и пунктуации, статусы C-классов. История — git commit + git tag `v{n+1}`.

- Правила C1–C5 описываются в config в пределах возможностей схемы и обработчиков `rule.py`; C1 имеет алгоритмическую реализацию в коде.
- Для каждого правила NO-CUT — **стабильный `id`**, чтобы diagnosis не зависел от позиции элемента в JSON-массиве.
- P1/P2, `terminal_set`, `min`, `pref`, `cap`, `min_merge`, `seam_classes_status`, `version` — с проверяемой схемой.

**При v{n+1} достаточно патча JSON только тогда, когда новое правило выражается уже поддерживаемой схемой. Новые операции/неподдерживаемые условия требуют изменения интерпретатора.**

## 3. Точные определения алгоритма

Нумерация токенов 1..n по Stanza id. **Позиция реза p** = «рез после токена p» (между токенами p и p+1), валидна при p < n; эквивалентно — «рез перед токеном p+1».

### 3.1 build_units

1. Корневое синтаксическое слово — слово с `head == 0` (в ожидаемом случае одно на предложение).
2. Для каждого прямого зависимого root (`word.head == root.id`) собрать его полное поддерево рекурсивно по `head`; `unit = [min_id, max_id]` этого поддерева.
3. Добавить отдельный unit корневого слова `[root.id, root.id]`.
4. `Word.id` — целое число. Не путать с `Token.id`: у поверхностного токена Stanza идентификатор MWT может задавать диапазон word-id.
5. **MWT не склеивать по совпадающей лемме**: брать реальный диапазон Word-ID, относящийся к одному `Sentence.tokens`-токену. Все позиции реза внутри этого диапазона запрещаются правилом `mwt` в NO-CUT.
6. Отсортировать units по `start_id`. Диапазоны unit могут пересекаться — ожидаемо для интервалов поддеревьев, само по себе не ошибка.

Для подсчёта `lex_words` — считать **поверхностные лексические токены**, а не отдельные `Word` внутри MWT. Пунктуация не считается лексическим словом.

### 3.2 C-классы

- **C1** — для каждого unit: рез после последнего его слова (`p = unit.max_id`), если `p < n`. После вычисления C1 все позиции внутри MWT всё равно удаляются NO-CUT.
- **C2** — перед синтаксическим словом с `deprel == "cc"`: `p = word.id - 1`.
- **C3** — перед целой PP-цепью при head-NOUN. Найти слово `t` с `deprel == "nmod"` и head с `upos == "NOUN"`; chain = поддерево `t` (ADP + все потомки, в т.ч. `case`/`appos` — см. config `chain: [case, nmod, appos]`). **Рез ставится перед ADP**: предлог всегда первый элемент PP-цепи (минимальный Word-ID), поэтому `first = min(word.id)` цепи = позиция ADP. Если `lex_left(p) >= 3` и `lex_right(p) >= 3` для `p = first - 1` — рез `p = first - 1`. Не перед первым *словом*, а перед всей цепью (включая ADP). **Пример K1**: `Arbeit an Heizungsanlagen,` → nmod = word(9), chain включает предлог(8) → p=7 (рез перед «an»); `Installation von Wasser-…` → nmod = word(17), chain включает предлог(16) → p=15 (рез перед «von»). Если резать только перед nmod-существительным (p=8 / p=16) — K1 не пройдёт 3/3 pass.
- **C4** — рез после корневого слова (`xpos ∈ {VAFIN,VVFIN}`), если непосредственно следующее по поверхности слово удовлетворяет `deprel ∈ {advmod,cc}` и одновременно (`xpos == KON` **ИЛИ** `lemma ∈ {denn,dann,so}`). Условия проверяются по соответствующим разным полям; `KON` — значение `xpos`, остальные значения — `lemma`. PTKNEG (например, `nicht`) в перечень не входит.
- **C5** — перед словом с `deprel == "mark"` и `xpos == "KOUS"`; рез `p = word.id - 1` разрешён, только если слева и справа от него ≥ 3 лексических поверхностных токенов.

`p` — позиция после слова `p` и перед словом `p+1`. `lex_left(p)` — число лексических поверхностных токенов целиком слева от позиции; `lex_right(p)` — целиком справа. Если позиция попадает внутрь MWT, она недопустима и не используется для C3/C5.

`S = (C1 ∪ C2 ∪ C3 ∪ C4 ∪ C5) − NO-CUT − P2`.

### 3.3 NO-CUT — запретные позиции реза

NO-CUT запрещает разрезать блок на соответствующей позиции. Наличие NO-CUT-ребра **внутри** блока нормально; ошибкой является только граница блока, совпавшая с запрещённой позицией.

Для каждого правила из `config.nocut` рассчитать запрещённые позиции и удалить их из `S`:

- **`det_to_noun`**: слово `d` с `deprel ∈ {det,det:poss,amod,nummod,compound,flat,appos}`, чей head имеет `upos == NOUN`. Запретить позицию между `d` и head только если они соседние по word-id.
- **`case_obl`**: слово `c` с `deprel == case`, head которого имеет `upos == NOUN` и `deprel ∈ {pobj,obl}`. Если `c` и head соседние — запретить позицию между ними.
- **`trunc_atomic_chain`**: для связанных цепочек NOUN с `xpos == TRUNC`, соединённых отношениями `cc`/`conj`, запретить все позиции между крайними word-id цепочки, чтобы нельзя было разделить её на части.
- **`mwt`**: запретить каждую позицию между Word-ID, принадлежащими одному поверхностному MWT-токену.
- **`aux_cop`**: для слова с `deprel ∈ {aux,aux:pass,cop}` запретить позицию между ним и head, если они соседние.
- **`root_aux`**: для root-глагола с `xpos ∈ {VAFIN,VVFIN,VVPP}` и его прямого зависимого с `deprel ∈ {aux,aux:pass}` запретить все позиции между их word-id, чтобы они не оказались в разных блоках.
- **`adv_part_pair`**: парные ADV/PART (лемматическая коррелятива) — рез между членами пары; конкретный список лемм решается отдельным кейсом (текущий config: `lemma_corr: true`). 

Каждое правило NO-CUT имеет стабильный строковый `id`. Диагноз ссылается на него, а не на индекс элемента массива.

Если несколько правил запрещают одну позицию — сохранить все соответствующие rule-id для diagnosis, позицию удалить из `S` один раз.

### 3.4 P1/P2 — пунктуация

- **P2**: каждый поверхностный токен, все Word-компоненты которого имеют UPOS `PUNCT` и который не входит в `terminal_set` (например, `-`, `,`, скобки), прикрепляется к предшествующему блоку. Поэтому позиция непосредственно перед ним запрещена: `p = first_word_id_of_punctuation_token - 1`, если у знака есть предшествующее слово.
- **P1**: конечный знак из `terminal_set` (`.`, `?`, `!`) прикрепляется к блоку с последним лексическим токеном. Запретить рез непосредственно перед этим знаком, чтобы не создавать блок только из терминальной пунктуации. **Исходный знак сохраняется; не добавлять точку автоматически поверх `?` или `!`.** После последнего токена позиция реза не создаётся.
- Если P2-знак оказался в начале предложения и у него нет предшествующего блока — сохранить его в первом блоке; не создавать пустой блок.
- Текст блока восстанавливать из исходной строки по offsets поверхностных токенов, а не простым соединением `Word.text` пробелами. Так сохраняются дефисы, пунктуация и исходные символы. У крайних пробелов в блоках затем удаляется whitespace при `check()`-сопоставлении.

### 3.5 Перечисление разбиений

1. Перебрать все подмножества допустимых позиций `S` в стабильном порядке по возрастанию списка позиций.
2. Преобразовать позиции в последовательные блоки поверхностного текста; применить правила P1/P2 и затем `min_merge`.
3. Проверить, что блоки не пусты, внешние границы не нарушают NO-CUT/P2, минимальный размер выполнен (кроме short-sentence exception), cap соблюдён.
4. Дедуплицировать одинаковые после нормализации разбиения. `rejected` — только уникальные варианты, сгенерированные из допустимых позиций `S`, но снятые проверками min/cap/структурной валидности; порядок детерминирован. Запретный разрез пользовательского разбиения **не появится** в этом переборе (его нет в `S`); он отражается в `check().diagnosis` как `forbidden`.
5. Сортировать валидные варианты по §3.8. Если валидных вариантов нет — `recommended` и `admissible` возвращаются пустыми, а не заполняются искусственным вариантом.

Число вариантов растёт экспоненциально с числом позиций `S`; для ожидаемых предложений это принимается как ограничение текущего референсного интерпретатора. Если потребуется лимит — отдельный явный параметр, не молчаливая обрезка.

### 3.6 min_merge (детерминированный, из config `min_merge`)

Для каждого блока, в котором `lex_words < min`:

1. Если блок содержит прямого зависимого root (`word.head == root.id`) — слить его со своим соседним блоком (root-блок расширяется; при двух соседах — тот, где меньше lex-слов; при равенстве — левый).
2. Иначе слить с соседним блоком, у которого меньше лексических слов; при равенстве выбрать левый блок, если левого нет — правый.
3. После каждого слияния пересчитать длины блоков и повторять, пока нет блоков короче `min` или пока разбиение не стало одним блоком.
4. Если лексических слов во всём предложении меньше `min` — разрешить единственный блок как **short-sentence exception**.
5. Слияние не может создавать новые позиции реза; итоговые границы — подмножество исходных позиций `S`.

Счётчик «число обязательных min-слияний» фиксировать до/во время применения алгоритма и использовать при rank. Параметры `prefer`, `else`, `tie` из config должны соответствовать ровно этому поведению; неизвестные значения — ошибка config.

### 3.7 cap_check

- Блок с более чем `cap` лексическими словами недопустим.
- Блок размером 6–7 слов (при `cap = 7`) допустим только если **каждая его внутренняя граница с соседними блоками**, кроме начала/конца предложения, соответствует легальной позиции C1–C5 и не совпадает с NO-CUT/P2.
- NO-CUT-ребро **внутри** блока не делает блок недопустимым; запрещена только граница разреза, попадающая на это ребро.
- Проверять границы после `min_merge` — оцениваются итоговые блоки.

### 3.8 rank (критерии статичны, не в config)

Сортировать валидные варианты по ключу с направлениями оптимизации:

1. **По возрастанию** — число блоков, длина которых не входит в `pref`.
2. **По возрастанию** — число обязательных min-слияний.
3. **По убыванию** — число unit, сохранённых целиком (большее число лучше).
4. **По возрастанию лексикографически** — отсортированный список позиций реза слева направо.

Эквивалентно ключу `(a asc, b asc, c desc, d asc)`. Ранг 1 = `recommended`; ранги 2+ = `admissible`. Поле `n` в объектах блоков — номер блока внутри сегментации; `rank` — глобальный ранг варианта.
## 4. Вход / парсинг + кэш

- **Ввод**: ровно одно предложение и config. Если Stanza разделил ввод на ноль или >1 предложение — завершить явной ошибкой в JSON/коде возврата; не объединять молча.
- **Парсинг**: Stanza depparse (German, `stanza==1.15.0`). Для зависимостей — `Sentence.words`: `Word.id` (int), `text`, `lemma`, `upos`, `xpos`, `feats`, `head`, `deprel`. Для поверхностного текста, пунктуации и MWT — `Sentence.tokens` + отображение токен→слова. **Не брать только `token.words[-1]`** — теряет прочие слова MWT.
  - В `parse_german` (MCP) MWT теперь отдаётся явно: каждому слову добавлены `is_mwt` (bool, из `Token.is_mwt()`) и `mwt_id` (диапазон Word-ID `[a,b]` для MWT), а параллельно список `tokens` (поверхностные токены с `is_mwt` и явным перечнем `word_ids`). rule.py берёт MWT-диапазоны из этих полей, а не перепарсит Stanza; сравнение допустимо только при совпадении модели/версии Stanza/препроцессинга (см. п. про кросс-проверку §4).
- `dep` во внутренних структурах — нормализованное имя `Word.deprel`. Для кросс-проверки с MCP `parse_german` сравнивать однозначно сопоставленные Word-ID и все поля; сравнение возможно только при совпадении модели, версии Stanza и параметров препроцессинга.
- **Environment (обязательно)**: Python 3.11; German depparse-модель — **offline** из кэша MCP, без скачивания в сеть. **Offline**: `Pipeline` с локальным каталогом моделей и `download_method=None`; кэш Stanza задаёт rule.py явно при запуске: `STANZA_CACHE_DIR=C:/Users/BIGTER/AppData/Local/StanfordNLP/stanza/Cache` (версия `1.15.0/resources/de`). Parse-кэш — отдельное место, `reference/cache/`.
- **Кэш разбора**: JSONL `text_hash → parse_json` в `reference/cache/`. Hash по UTF-8; в ключ включать идентификатор/версию модели и параметры parsing, чтобы не использовать parse от другой модели. Записанный parse — артефакт для повторяемости.
- Разделять **model resources** (локальные файлы Stanza, обязательны даже offline) и **parse cache** (ускоряющий кэш конкретных разборов). «Без кэша» = запуск без parse cache, но с теми же локальными model resources.

## 5. Пайплайн (детерминированный)

1. Проверить config по схеме и версии; неизвестные ключи/операторы условий — ошибка, не игнорирование.
2. `parse` → `Sentence.words` для синтаксиса и `Sentence.tokens` для surface/MWT mapping.
3. `build_units`.
4. Вычислить `seams = union(c1..c5(words, config))`.
5. Вычислить все позиции NO-CUT и P2; `S = seams − NO-CUT − P2`.
6. Перебрать подмножества `S`; сформировать блоки из исходного текста, выполнить P1/P2 и `min_merge`.
7. Проверить пустые блоки, минимальный размер (с short-sentence exception), cap, отсутствие NO-CUT/P2 на итоговых границах.
8. Отбракованные варианты сохранить в `rejected` с причинами; валидные ранжировать по §3.8.
9. Вернуть JSON по §8: первый по рангу — `recommended`, остальные — `admissible`.

## 6. Детерминизм

- Один input + одинаковые байты config + та же версия Python/Stanza/модели → один и тот же output.
- Для SHA-256 сериализовать JSON в UTF-8 с `sort_keys=True`, фиксированными separators, без временных полей/путей; порядок массивов вариантов также детерминирован.
- В протоколе теста фиксировать hash входного текста, hash config, версию Python/Stanza, идентификатор модели. Сравнивать два вывода в одинаковом окружении.
- Повторить сравнение с включённым и отключённым/пустым **parse cache**; model resources — те же локальные файлы.
- Нет случайности и LLM-opinions внутри `rule.py`. Изменение содержимого модели или конфигурации — другой вход, прежний hash не обязан совпадать.

## 7. Версионирование / синк с RULE.md

- `config.json` — единый файл без номера; внутреннее `"version"` — версия правила.
- `rule.py` стабилен при изменении параметров/условий, уже поддерживаемых схемой. Новые типы правил/операций — изменение кода + тесты.
- **Синхронизация:** при v{n+1} обновить `RULE.md` и `config.json`, пройти проверки, затем git commit + tag `v{n+1}`.
- **Config completeness:** каждое нормативное правило из `RULE.md` должно быть либо выразимо в config и поддержано `rule.py`, либо явно помечено как неподдерживаемое с fail. Статические алгоритмические процедуры (`build_units`, rank и т.п.) не обязаны дублироваться в JSON, но должны быть отражены в схеме/тестах.

## 8. Выход JSON + `check()`

### 8.1 Выход JSON (точный формат)

```json
{
  "language": "de",
  "rule_version": "v3",
  "recommended": [
    {"n": 1, "text": "Ich weiß es,", "lex_words": 3, "toks": [1,2,3,4], "seams": ["C5"]},
    {"n": 2, "text": "weil er müde ist.", "lex_words": 4, "toks": [5,6,7,8,9], "seams": []}
  ],
  "admissible": [],
  "rejected": [{"variant":"","violations":["NO-CUT: det(1)->NOUN(2)"]}],
  "seam_classes_status": {"C1":"verified","C2":"verified","C3":"verified","C4":"verified","C5":"verified"}
}
```

- `recommended` — только ранг 1 (один вариант).
- `admissible` — остальные валидные варианты.
- `rejected` — с `violations`; порядок детерминирован.
- `text` блока = исходный текст токенов (включая знаки); `toks` — list Word-ID; `seams` = классы, по которым сделан рез после этого блока; у последнего блока — пусто.

### 8.2 `check()`: API для цикла «разбивка → правило» (soft match)

`rule.py --check "<sentence>" --blocks "block1" "block2" ... [--config reference/config.json]`

- **Совпадение (soft):** `match=true`, если human blocks == `recommended[0]` **ИЛИ** human ∈ `admissible`. Сопоставление — строгое по тексту блоков (нормализация: trim + collapse whitespace); порядок и количество совпадают.
- `human_rank` — 1 (строгого) / N (в admissible, ниже rank1) / null.
- Диагноз строится **из тех же результатов пайплайна** (§5), а не из отдельной эвристики. Для каждой границы human-разбиения присвоить статус с приоритетом: **`forbidden`**, если граница запрещена NO-CUT/P2; иначе **`missing`**, если граница не принадлежит C1–C5; иначе указать effect, из-за которого вариант невалиден/не ранжирован так же.
- `forbidden.rule` — стабильный `id` правила config (например, `aux_cop`), не числовой индекс массива.

```json
{
  "match": false,
  "human_rank": null,
  "rule_version": "v3",
  "recommended": [
    {"n": 1, "text": "Ich weiß es,", "lex_words": 3, "toks": [1,2,3,4], "seams": ["C5"]},
    {"n": 2, "text": "weil er müde ist.", "lex_words": 4, "toks": [5,6,7,8,9], "seams": []}
  ],
  "admissible": [],
  "diagnosis": {
    "cuts": [
      {"pos": 7, "between": "müde | ist", "status": "forbidden", "rule": "aux_cop"}
    ],
    "effects": {"min_merge": [], "cap": []}
  }
}
```

- `match=true` → `diagnosis=null`, `human_rank` ∈ {1, N}.
- **`missing`** = граница не подпадает ни под один C-класс и не запрещена NO-CUT/P2. `features` — Stanza-поля слова справа от границы (`p+1`): `id`, `text`, `lemma`, `upos`, `xpos`, `feats`, `head`, `deprel`.
- **`forbidden`** = граница попадает на NO-CUT или P2. В `rule` — стабильный rule-id; для P2 — отдельный идентификатор, например `punct_p2`.
- **`effects.min_merge/cap`** объясняет изменение/отбрасывание варианта. Если human-разбиение содержит пустой блок, нарушение `min` или превышение `cap` — отражается в диагнозе.

Пример для v3. `id` у каждого правила NO-CUT стабилен и используется в diagnosis; списки значений сравниваются точно и с учётом регистра, если не указано иное.

## 10. Проверки и критерии корректности

- **`self_test()`** — правило воспроизводит все verified-кейсы `CORPUS/verified.jsonl` (`accepted=true`). **Критерий pass (soft match):** human blocks == `recommended.blocks` **ИЛИ** human blocks == `blocks` любого варианта из `admissible`; текст нормализовать (`trim` + `collapse whitespace`), порядок и количество блоков совпадают. Вывод — pass/fail по каждому кейсу.
- **`check()`** — 3 corpus cases → match=true; 1 «сломанный» кейс (рез внутри NO-CUT) → match=false, diagnosis status=forbidden, ожидаемый rule-id.
- **Determinism check** — один input → один output (sha256, §6).
- **Config completeness** — все настраиваемые условия из `RULE.md` покрыты config и поддерживаемыми обработчиками; статические алгоритмические процедуры покрыты кодом и тестами. Неизвестные операторы → fail. **Нельзя подтверждать полноту без сверки с `RULE.md`.**
- **Exact golden test** — отдельно проверять, что `recommended` для K1–K3 совпадает с эталонными блоками §15. Строже, чем soft-match `self_test()`.
- **New case verification** — новый ground-truth-кейс классифицируется как совпадение или gap; диагноз объясняет расхождение.
- **Regression 100%** — каждый verified-кейс проходит soft-match `self_test()`, отдельные golden tests фиксируют rank-1 output.

## 11. Acceptance / Definition of Done (все одновременно)

| # | Условие | Как проверить |
|---|---|---|
| 1 | `rule.py` существует, запускается (`python reference/rule.py "…"`, **и** `--check ... --blocks ...`), выводит §8 JSON | run + §8 |
| 2 | `self_test()` = **3/3 pass** по текущему `CORPUS/verified.jsonl` (soft match) | `python reference/rule.py --self-test` |
| 3 | **check()**: 3 corpus cases → match=true; 1 «сломанный» кейс (рез внутри NO-CUT) → match=false, diagnosis status=forbidden верно | §8.2 |
| 4 | Determinism check passes (sha256 identical) | §6 |
| 5 | Config completeness passes | §10 |
| 6 | Запуск без parse-кэша (при тех же локальных model resources и версии модели) даёт тот же результат | §6 |

Точное совпадение `recommended` с K1–K3 (golden) — отдельный тест. **Нельзя заявлять Config completeness, пока не сверены `RULE.md` и реальный `reference/config.json`.**

## 12. Workflow v{n+1} — цикл check → delta → match

1. Человек даёт ground-truth-кейс (по PROMPT, может быть пакетом).
2. **`rule.py --check`** sentence+blocks → match? diagnosis?
   - **match=true** (soft: recommended rank1 или admissible) → шаг 5.
3. **match=false** → LLM готовит **минимальную дельту** по facts из diagnosis (missing → новый C-класс/исключение; forbidden → исключение в NO-CUT; effects → min_merge/cap), патчит `config.json`; `rule.py` не трогаем.
4. Повтор: **`rule.py --check`** + `self_test()`. **Max 5 попыток**; после 5 без match — report человеку (diagnosis, текущий config, варианты).
5. **Regression:** `self_test()` → 100% pass по всему корпусу.
6. Человек подтверждает разбивку → CORPUS: новый verified-кейс; `LOG/iterations` (строка + история), GAPS (GAP → resolved); git commit + tag v{n+1}.
7. Config до commit — черновик; при неудаче в цикле откатывается.

## 13. Ограничения / гейты

- **Только поля Stanza**: у синтаксических слов — `id,text,lemma,upos,xpos,feats,head,deprel`; связь с поверхностным токеном/MWT — отдельно. Во внутреннем формате `dep` = нормализованный `deprel`. Никакой семантики, пауз, LLM-opinions в `rule.py`.
- **Детерминизм**: один input → один output; кэш по hash текста (факт, не «кэш»).
- **Правило = данные в пределах поддерживаемой схемы**: при v{n+1} патчится `config.json`, если новое условие уже поддержано `rule.py`; новая операция требует изменения кода и тестов.
- **Формат вывода** — §8.

## 14. Edge cases

- **MWT** — использовать реальные Word-ID диапазоны одного поверхностного Stanza Token; запрещать резы внутри диапазона. Не выводить MWT по совпадающей лемме, не брать только `token.words[-1]`.
- **Punctuation**: P1 = last token; P2 = non-terminal → prev block. Терминальный знак сохраняется как есть.
- **Cap**: блок 6–7 слов допустим только при легальных внешних границах; NO-CUT внутри блока допустим, на границе — нет.
- **Min**: блок <3 → merge детерминированно; если всё предложение короче `min` — один блок (short-sentence exception).
- **Empty blocks** — не допускаются.
