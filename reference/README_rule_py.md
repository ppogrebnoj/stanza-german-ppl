# rule.py — архитектура (архив ТЗ v3)

**Статус.** Архивное техническое задание на проектирование `reference/rule.py`
(строка 4 в LOG/iterations.md, v3.impl). Задача выполнена; файл сохранён только
как история архитектурных решений. Детали текущего поведения — по ссылкам ниже.

## Два слоя: данные vs код

- **Правило = данные** (`reference/config.json`): условия C1..Cn, NO-CUT, P1/P2,
  min/pref/cap, `rank.criteria`. При v{n+1} — патч JSON.
- **Алгоритмическая семантика = код** (`rule.py`): build_units, seams, NO-CUT,
  p2, min_merge, cap_check, rank — не правятся в config; новые операции/типы
  условий требуют изменения кода + тестов.

Граница конфигурируемости: что в config — патчится дельтой LLM; чего нет —
`config_completeness()` обязан выявить (не считать «полным» молча).

## Два режима: судья vs мнение машины

- `check() = СУДЬЯ`: verdict по разбивке человека — резы покрыты C1..Cn и не на
  NO-CUT/P2, блоки min/cap, полное покрытие. Ранжирование в verdict **не входит**.
- `run() = МНЕНИЕ МАШИНЫ` (перебор §8 RULE.md): recommended/admissible/rejected +
  ранг; критерии ранга — данные `config.rank.criteria`, не код.
- Ground truth = разбивка человека; ранг машины — только «сигнализация».

## Детерминизм

Один input + одинаковые байты config + та же версия Python/Stanza/модели →
один и тот же output (sha256, canonical JSON). Проверяется CLI-гейтом
`--determinism` (сравнение с включённым/выключенным parse-кэшем).

## Версионирование

Правило = единый RULE.md; версия = git tag v{n+1}; история — LOG/iterations.md.
Config = единый config.json без номера, внутренний `"version"` = версия правила.
PROMPT/PROLOG обновляются только вместе с правилом.
