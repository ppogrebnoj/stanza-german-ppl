# Требования к новой машине

Что должно стоять **до** запуска скриптов проекта, кто это ставит, как проверить и что делать,
если условие не выполнено. Ставит **пользователь** (установщики требуют его согласия и иногда
прав администратора); проект берёт на себя всё после первого скрипта.

## 1. Обязательный минимум

| Компонент | Поддерживаемый диапазон | Проверено на | Зачем |
|---|---|---|---|
| **Python x64** | **3.11 – 3.15** | 3.11.0 · 3.13.15 · 3.14.10 · 3.15.2 | правило, валидатор, стенд, MCP-сервер |
| **Git** | ≥ 2.30 | 2.55.0.windows.5 | история, обновления, хук pre-commit |
| **`gh` CLI** | ≥ 2.40 | 2.103.3 | доступ к приватному репозиторию и ассетам релиза |

Нижние границы не случайны: `numpy 2.4.6` публикуется с `cp311`, в коде используется
`Path.write_text(newline=)` (Python ≥ 3.10), `gh release download` с `-p` и `gh api` — в `gh` ≥ 2.40.

Про git-настройки Windows: `core.autocrlf=true` (так по умолчанию в Git for Windows) проекту
**не мешает** — в репозитории есть `.gitattributes` с `* text=auto eol=lf`, атрибуты сильнее
`autocrlf`, поэтому файлы и на новой машине будут с LF (проверено свежим клоном). `core.longpaths`
и SSH-ключи не нужны: пути короткие, доступ по HTTPS.

> **Если на машине Python 3.15+** (например, 3.15.2): проект на нён **не соберётся** — у `torch 2.14.0`
> колёса до cp314, у `numpy 2.4.6` — тоже до cp314. Ставится **рядом** 3.13:
> `winget install --id Python.Python.3.14 -e --accept-package-agreements` — текущая версия не
> трогается, `setup.ps1` сам выберет 3.11 (если есть) либо 3.13/3.14. Поднимать пины `torch`/`numpy`
> ради 3.15 нельзя: это меняет окружение, на котором сняты F1 0.777/0.686.
> `setup.ps1` проверяет диапазон **до** создания venv и сразу печатает эту команду;
> `doctor` даёт FAIL с той же подсказкой.

**Почему «последняя версия Python» — это нормально.** Колёса под пины уже есть:
`torch 2.14.0` — cp310…**cp314**, `numpy 2.4.6` — cp311+, `stanza`/`mcp`/`pyphen` — чистый Python.
Установка идёт на любой версии 3.11–3.14; `requirements.txt` разрешается на 3.11 и 3.13
(проверено `pip install --dry-run`). Цифры F1 сняты на **3.11** — `doctor` на другой версии
выдаёт WARN, но не блокирует.

### Что стоит на машине → что делать

| На машине | Действие |
|---|---|
| Python **3.11–3.15** x64 (в т.ч. «последний») | ничего, проект ставится как есть (для 3.15 скрипт сам возьмёт `requirements-py315.txt`) |
| Python **3.16+** | поставить рядом **3.15** (или 3.14): `winget install --id Python.Python.3.15 -e`; текущую версию это не трогает, `setup.ps1` выберет поддерживаемую |
| Python **≤3.10** | то же: поставить 3.15 рядом |
| Python **32-bit** | поставить x64-сборку той же версии |
| `python` открывает Microsoft Store (заглушка) | поставить Python с python.org; заглушку отключить в «Настройки → Приложения → Псевдонимы выполнения» |
| Несколько Python в PATH | не важно: `setup.ps1` ищет `py -3.11` → `python3.11` → `python`, а `doctor` печатает, каким именно шёл прогон |

Как узнать, что установлено:

```powershell
py -0                                    # все версии, звёздочкой — версия по умолчанию
python --version                         # что именно получит setup.ps1, если py -3.11 нет
where python                             # откуда он берётся (и не заглушка ли это)
```

### Установка (Windows, winget)

```powershell
winget install --id Python.Python.3.15 -e --accept-package-agreements   # или 3.11 / 3.13 / 3.14
winget install --id Git.Git -e --accept-package-agreements
winget install --id GitHub.cli -e --accept-package-agreements
```

Все три идентификатора проверены в каталоге winget. Без winget — официальные установщики:
python.org · git-scm.com (Git for Windows, тянет Git Credential Manager) · cli.github.com.

**Права:** администратор нужен только для установки в `Program Files`. Для проекта админ не
требуется: пишем в каталог проекта, `%LOCALAPPDATA%\StanfordNLP` и `%USERPROFILE%\.lmstudio`.
Python можно ставить per-user (`winget install --scope user`, либо установщик python.org →
«Install for me only») — тогда прав администратора вообще не нужно.

### Проверка (30 секунд)

```powershell
py -0                                                    # список версий: нужна 3.11–3.14
git --version                                            # ≥ 2.30
gh --version                                             # ≥ 2.40
python -c "import platform,sys; print(platform.architecture()[0], sys.version.split()[0])"
                                                         # 64bit и 3.11–3.14
gh auth status                                           # ✓ Logged in … (если нужен приватный доступ)
```

## 2. Доступ к приватному репозиторию — три способа

Репозиторий `ppogrebnoj/stanza-german-ppl` приватный, релиз `models-v1` тоже. Доступ выдаётся
**через API**, токен нигде не сохраняется в открытом виде (используется credential helper `gh`).

### Способ A — токен на новой машине (основной)

1. Владелец/пользователь создаёт **fine-grained PAT** на github.com → Settings → Developer settings →
   Personal access tokens → Fine-grained:
   * Repository access: **Only select repositories** → `stanza-german-ppl`
   * Permissions → **Contents: Read-only** (этого достаточно и для кода, и для скачивания ассетов релиза)
   * Expiration: 7–30 дней.
2. На новой машине токен передаётся в `gh` без сохранения в истории:

   ```powershell
   "ВСТАВИТЬ_ТОКЕН" | gh auth login --with-token
   gh auth setup-git          # git будет ходить через gh (credential helper)
   ```

3. Дальше всё как обычно: `git clone https://github.com/ppogrebnoj/stanza-german-ppl.git C:\KI_WORK`
   и `scripts/unpack_models.py --release models-v1`.

Разово, вообще без `git` (только исходники + модели по API):

```powershell
gh api repos/ppogrebnoj/stanza-german-ppl/zipball/master > src.zip
gh release download models-v1 -p "stanza-models-*.zip*" -D .
```

### Способ B — владелец выдаёт доступ по API

На машине владельца (одна команда, вместо ручного «Settings → Collaborators»):

```powershell
# пригласить пользователя с правом чтения
gh api -X PUT repos/ppogrebnoj/stanza-german-ppl/collaborators/<github-username> -f permission=read
# проверить, кто уже имеет доступ
gh api repos/ppogrebnoj/stanza-german-ppl/collaborators --jq '.[].login'
```

Пользователь принимает приглашение (письмо/GitHub) и клонирует репозиторий — токен вручную
не нужен, `git` использует Git Credential Manager / браузерную авторизацию.

### Способ C — доступа нет совсем

Работает без токена и без прав: офлайн-набор (git bundle + zip моделей + колёса), см.
`НОВАЯ_МАШИНА.md` §4. Владелец собирает его на машине с доступом, переносит файлами.

## 3. Сеть

| Хост | Порт | Что нужно |
|---|---|---|
| `github.com`, `api.github.com` | 443 | клон, API, релиз |
| `codeload.github.com`, `objects.githubusercontent.com` | 443 | скачивание архива/ассетов |
| `release-assets.githubusercontent.com` | 443 | сам файл моделей (315 МБ) |
| `pypi.org`, `files.pythonhosted.org` | 443 | зависимости (≈2.5 ГБ загрузок) |

Прокси: `HTTPS_PROXY` / `HTTP_PROXY` в окружении (уважают `pip`, `gh`, `git` — для `git`
дополнительно `git config --global http.proxy <url>`). Внутренний индекс PyPI вместо pypi.org:
`pip install -i <url> -r requirements.txt` (пункт плана U2 — параметр в `setup.ps1`).

Обрывы соединения не критичны: `pip` ретраит сам, `unpack_models.py` — 3 попытки, `git clone`
пригодится повторить вручную.

## 4. Диск, память, время

| Ресурс | Требование | Пояснение |
|---|---|---|
| Свободно на диске | **≥ 4 ГБ** | venv 0.78 ГБ + кэш pip до 2.5 ГБ (чистится: `python -m pip cache purge`) + модели 0.31 ГБ |
| ОЗУ | ≥ 4 ГБ | torch CPU в работе ~1 ГБ |
| Время установки | 8–15 мин | при нормальной сети; основное — pip (torch ≈ 200 МБ) |
| Путь установки | любой, **кроме** `Program Files` и синхронизируемых облаком каталогов | пробелы и кириллица в пути проверены — работают |

## 5. Что НЕ требуется (чтобы не ставили лишнее)

| Не нужно | Почему |
|---|---|
| SSH-ключи | доступ по HTTPS: `gh`-credential helper или Git Credential Manager |
| `git-lfs`, `gpg` | в репозитории нет LFS-объектов и подписи коммитов |
| Node.js / npm | скрипты проекта — Python и PowerShell; в коде нет обращений к `node`/`npm`/`npx` (проверено поиском). Если Node уже стоит (например, 26.x) — он не мешает и ничего не ускоряет: MCP-сервер проекта — Python-stdio, а не npm-пакет |
| Visual Studio Build Tools / компилятор C++ | все зависимости приходят колёсами (бинарные) |
| Docker | сервер работает как локальный процесс, контейнер ничего не упрощает |
| Права администратора | нужны только установщикам Python/Git, если ставить «для всех пользователей» |
| Клиент MCP (LM Studio и др.) | нужен для работы в чате, но не для правил, валидатора и стенда |

## 6. Кто что делает

| Шаг | Кто | Команда |
|---|---|---|
| 1. Поставить Python / Git / gh | **пользователь** (по согласию, возможно с правами админа) | `winget install …` (см. §1) |
| 2. Выдать доступ или токен | владелец репозитория / пользователь | §2, способ A или B |
| 3. Развернуть проект | скрипты | `setup.ps1` → `unpack_models.py --release models-v1` → `install_mcp.py` |
| 4. Принять работу | скрипты | `doctor.py` (FAIL 0) + `smoke_test.py --full` |

После появления пункта U1 плана шаги 3–4 схлопываются в одну команду:
`powershell -File scripts\install.ps1` (сам проверит окружение по §1 и позовёт остальные скрипты).
