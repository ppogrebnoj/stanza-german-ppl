# ПРОТОКОЛ — цикл доработки правила (немецкая сегментация по Stanza)

Цель цикла: человек даёт разбивку предложения → LLM корректирует правило по промту **PROMPT.md**. После достаточного числа итераций правило = ТЗ для программирования. Сейчас работаем только над правилом и промтом.

## Файлы цикла
| Файл | Назначение |
|---|---|
| `RULE.md` | Текущее правило (единый файл, v3; версия в шапке). История версий — git-теги + LOG/iterations. |
| `reference/config.json` | Машинальная версия правила: условия C1..C5 / NO-CUT / P1-P2 через Stanza-признаки, параметры min/pref/cap. Единый файл (без номера); версия — внутреннее поле `"version"`. Дельта LLM = патч конфига. |
| `PROMPT.md` | Промт для LLM (вход, шаги, секции вывода). |
| `CORPUS/verified.jsonl` | Хранимый корпус verified-разбиений человека (ground truth); по 1 кейсу на строку. Схема-пример — отдельный файл `CORPUS/schema.jsonl`, в регресс не входит. |
| `GAPS/registry.md` | Реестр GAP-типов, сформулированных только через Stanza-признаки. |
| `LOG/iterations.md` | Лог итераций + история правил (единый файл): секция 1 — таблица всех итераций (счётчик N, регресс); секция 2 — детальная история изменений правил по версиям. |
| `reference/rule.py` | Детерминированный референс-интерпретатор + `self_test()` (создаётся отдельной дельтой, по `reference/TZ_rule_py.md`). |

## Гейт приёма ground truth (вердикт → приём)
Разбивку человека принимаем как **verified** только если:
1. **Детерминированность** — разбивка воспроизводится правилом детерминированным способом (seam-множество, P1/P2, min/cap).
2. **Только Stanza-поля** — обоснование резов/объединений выражено только через Stanza-признаки (`deprel/xpos/lemma/is_mwt`), без семантики и пауз.
3. **Ноль регресса** — новая версия правила воспроизводит все ранее verified-кейсы `CORPUS/verified.jsonl`; конфликты разрешаются явным решением (запись в `GAPS/registry.md`).

## Итерация
После вердикта человек: принимает / корректирует разбивку → LLM пишет дельту, обновляет `RULE.md` и `config.json`, `CORPUS/verified.jsonl`, `GAPS/registry.md`, `LOG/iterations.md` (таблица + история); **git commit + tag v{n+1}** после каждой дельты.

## Версионирование
- Правило — единый файл: **RULE.md** (версия в шапке). История: git-теги (v1..vN) + LOG/iterations. Отдельных файлов на версии нет.
- Конфиг — единый файл: **config.json** (без номера); внутреннее `"version"` = версия правила; история через git-commit.
- PROMPT.md обновляется только вместе с правилом (при необходимости).

## Счётчик N
N = номер последней зафиксированной версии правила (таблица в `LOG/iterations.md`). Текущая базовая — **v3**, N=3.

## Критерии выхода в ТЗ для программирования
Выход допустим только когда **все** условия выполнены:
1. **>=20 verified-кейсов** в `CORPUS/verified.jsonl` (accepted=true).
2. **GAP-реестр: все resolved + все seam-классы verified** — каждый gap = resolved, а все C1–Cn = verified. Замечание: «resolved» ≠ «verified»: критерий №2 — необходимое, а не достаточное условие.
3. **Последние 3 итерации — только уточнения**: без новых seam-классов (C5… не добавляются) и без изменения NO-CUT/P1/P2.
4. **Регресс 100%** — все verified-кейсы воспроизводятся текущей версией правила без конфликтов.
